Inside the PE File Format: A Deep Dive

Mustafa Al-Zaareer Lv1
  2026-04-02 17:35:31 2026-04-02 17:35:31 Created   2026-04-02 22:18:03 2026-04-02 22:18:03 Updated  

Introduction

What is this?
This post is a deep dive into the Portable Executable (PE) file format. We’ll explore how PE files are structured on disk and how they are mapped and loaded into memory.

Why we need to learn the PE file format?
Knowledge of the PE file format is fundamental for anyone working in reverse engineering or malware analysis. Many techniques used in both fields rely heavily on how executables are structured and loaded into memory. Without a clear understanding of PE internals, it becomes difficult to properly analyze binaries, identify suspicious behavior, or understand how certain techniques are implemented.

Overview of PE file structure

PE files
PE stands for Portable Executable, it’s a file format for executables used in Windows operating systems,not only .exe files are PE files, dynamic link libraries (.dll), Kernel modules (.srv) and many others are also PE files.

A PE file is a data structure that contains all the information required by the operating system loader to map the executable into memory and start its execution.

PE Structure Overview

A typical PE file follows a well-defined structure, as illustrated in the figure below:

DOS Header
Every PE file starts with a 64-byte structure called the DOS header, which enables the file to be identified as a valid MS-DOS executable.

DOS Stub
Following the DOS header is the DOS stub, a small MS-DOS–compatible program whose only purpose is to display the message “This program cannot be run in DOS mode” if the executable is run in a DOS environment.

NT Headers
The NT Headers structure contains three main components:

  • PE Signature: A 4-byte magic value used to validate the file as a PE format.
  • File Header (COFF Header): Holds metadata about the binary, including target machine, number of sections, and characteristics.
  • Optional Header: The core of the PE structure. While optional for object files, it is required for executable images. It defines key attributes such as the entry point, image base, and memory alignment, all of which are used by the OS loader during execution.

Section Table
The Section Table, located directly after the Optional Header, is an array of Image Section Headers. Each header describes a section in the PE file, including its size, location, and characteristics.

Sections
Sections store the real content of the PE file, such as code, data, and resources. Each section has its own purpose and is described by a header in the Section Table.

PE-bear
To understand the PE file structure, it helps to visualize it with a PE viewer. My personal favorite is PE-bear, which we’ll use in this post to examine the different headers and sections.

Looking at the left panel of PE-bear, the structure of this sample file becomes clear, showing headers and sections just as described.

Headers

DOS Header

The DOS header, also called the MS-DOS header, is a 64-byte structure located at the very start of a PE file.

While it’s not essential for the functionality of PE files on modern Windows systems, it exists for backward compatibility. This header identifies the file as an MS-DOS executable. If the file is loaded on an MS-DOS system, the DOS stub gets executed instead of the actual program. Without this header, attempting to run the executable on MS-DOS would fail, producing a generic error.

Structure
The DOS header is defined in winnt.h as the IMAGE_DOS_HEADER structure:

Most of the members in this structure are only relevant for MS-DOS, but a few are critical for Windows PE loading. The key members are:

  • e_magic: The first member of the DOS header, a 2-byte WORD. It’s called the magic number and has a fixed value of 0x5A4D (MZ in ASCII). It serves as the signature that identifies the file as an MS-DOS executable.
  • e_lfanew: Located at offset 0x3C in the DOS header, this member holds the offset to the start of the NT headers. On Windows systems, this is crucial for the PE loader because it tells the loader where to find the File Header and Optional Header.

We can view the contents of the DOS Header using PE-bear on our sample PE file:

As you can see, the first member of the header is the magic number, which has the fixed value 0x5A4D (MZ) that we discussed earlier.

The last member of the DOS Header, located at offset 0x3C, is labeled “File address of new exe header” (e_lfanew). In our sample file, it has the value 0xB0. If we navigate to that offset in the file, we find the start of the NT Headers, just as expected.

DOS Stub

The DOS stub is a small MS-DOS program embedded in the PE file. Its only purpose is to display an error message if the executable is run in a DOS environment and then exit. By default, this message is:

“This program cannot be run in DOS mode.”

Rich Header

Now that we’ve explored the DOS Header and DOS Stub, there’s still a chunk of data sitting between the DOS Stub and the start of the NT Headers that we haven’t covered yet.

This chunk is commonly known as the Rich Header. It’s an undocumented structure present only in executables built using the Microsoft Visual Studio toolset. The Rich Header contains metadata about the tools used to compile the executable, including tool names, types, versions, and build numbers.

Interestingly, most resources on PE files don’t mention the Rich Header at all. That makes sense because it isn’t strictly part of the PE format — it can even be zeroed out without affecting the executable’s functionality. Microsoft includes it mainly for internal build tracking.

Structure of the Rich Header
The Rich Header is made up of:

  • XORed data
  • Signature (Rich)
  • 32-bit checksum (used as the XOR key)

The encrypted data starts with a DWORD signature DanS, followed by three zeroed-out DWORDs for padding. After that, it contains pairs of DWORDs, each representing an entry. Each entry records:

  • The tool ID (high WORD of the first DWORD) or product ID
  • The build ID (low WORD of the first DWORD)
  • The use count (second DWORD of the pair)

PE-bear parse the Rich Header automatically, so you can inspect it without manual decoding.

NT Headers

The NT Headers are defined in winnt.h as the IMAGE_NT_HEADERS structure. Looking at its definition, we can see that it consists of three main members:

  1. DWORD Signature – Identifies the file as a PE file.
  2. IMAGE_FILE_HEADER FileHeader – Contains general information about the PE file, such as the target architecture and the number of sections.
  3. IMAGE_OPTIONAL_HEADER OptionalHeader – Provides essential information for the OS loader, including the entry point, memory layout, and required libraries.

It’s worth noting that there are two versions of this structure:

  • IMAGE_NT_HEADERS for 32-bit executables (PE32)
  • IMAGE_NT_HEADERS64 for 64-bit executables (PE32+)

The main difference between the two is the version of the Optional Header they use:

  • IMAGE_OPTIONAL_HEADER32 for 32-bit executables
  • IMAGE_OPTIONAL_HEADER64 for 64-bit executables

This distinction ensures that the PE loader can handle both 32-bit and 64-bit executables correctly.

Signature
The first part of the NT Headers is the PE signature. This is a 4-byte (DWORD) value that identifies the file as a Portable Executable. Its fixed value is 0x50450000, which corresponds to PE\0\0 in ASCII. This signature acts like a marker, letting the Windows loader know where the PE-specific structures begin.

File Header
The File Header is a simple structure that stores basic information about the PE file. It’s defined in winnt.h as IMAGE_FILE_HEADER:

This structure contains 7 members, each with a specific role:

  • Machine: Indicates the CPU architecture that the executable targets. Common values are 0x8664 for AMD64 and 0x14c for i386.
  • NumberOfSections: The total number of sections in the PE file (or the size of the Section Table).
  • TimeDateStamp: A timestamp showing when the file was created, stored as a Unix time value.
  • PointerToSymbolTable and NumberOfSymbols: These fields point to the COFF symbol table and indicate the number of entries, but they are usually set to 0 because COFF debugging information is deprecated.
  • SizeOfOptionalHeader: The size of the Optional Header following this File Header.
  • Characteristics: Flags that describe the file’s attributes, such as whether it’s executable, a system file, or a library.

Optional Header
The Optional Header is the most critical part of the NT Headers. The Windows PE loader relies on this header to find the information it needs to load and execute the program correctly. it’s mandatory for executable image files. Its size is not fixed, which is why the SizeOfOptionalHeader member in the File Header exists.

Structure Overview
The first few members of the Optional Header are standard across all COFF implementations, while the remaining members are Windows-specific extensions. These extra fields are required by the Windows loader and linker to properly handle executables.

There are two versions of the Optional Header:

  • IMAGE_OPTIONAL_HEADER32 – used for 32-bit executables
  • IMAGE_OPTIONAL_HEADER64 – used for 64-bit executables

The differences between the two are mainly:

  1. Number of members – PE32 has 31 members, while PE32+ has 30. PE32 includes a BaseOfData field, which marks the start of the data section in memory.
  2. Data types for certain fields – In PE32+, five members that are DWORD in 32-bit are ULONGLONG in 64-bit:
    • ImageBase
    • SizeOfStackReserve
    • SizeOfStackCommit
    • SizeOfHeapReserve
    • SizeOfHeapCommit

The definition of both structures:

Structure members:

  • Magic – Identifies the file type:
    • 0x10B → PE32 (32-bit)
    • 0x20B → PE32+ (64-bit)
    • 0x107 → ROM image
      This field determines whether the executable is 32-bit or 64-bit. The Machine field in the File Header is ignored by the loader.
  • MajorLinkerVersion / MinorLinkerVersion – Linker version numbers.
  • SizeOfCode / SizeOfInitializedData / SizeOfUninitializedData – Sizes of the code, initialized data, and uninitialized data sections.
  • AddressOfEntryPoint – The relative virtual address (RVA) where execution begins. For DLLs, this may be zero.
  • BaseOfCode / BaseOfData (PE32 only) – RVAs of the code and data sections.
  • ImageBase – Preferred memory address for the image. Modern systems often relocate the image due to ASLR or other memory constraints.
  • SectionAlignment / FileAlignment – Control how sections are aligned in memory and on disk.
  • Version fields – MajorOperatingSystemVersion, MinorOperatingSystemVersion, MajorImageVersion, MinorImageVersion, MajorSubsystemVersion, MinorSubsystemVersion specify OS, image, and subsystem versions.
  • SizeOfImage / SizeOfHeaders – Total image size and total size of headers, rounded up to alignments.
  • Subsystem – Specifies the required Windows subsystem for this executable.
  • DllCharacteristics – Flags defining runtime characteristics, such as NX support or relocatability.
  • Stack and Heap sizes – SizeOfStackReserve, SizeOfStackCommit, SizeOfHeapReserve, SizeOfHeapCommit define memory allocation for the stack and heap.
  • LoaderFlags / Win32VersionValue – Reserved fields, usually set to zero.
  • NumberOfRvaAndSizes – The number of entries in the DataDirectory array, which holds important tables like imports, exports, and relocations.
  • DataDirectory: An array of IMAGE_DATA_DIRECTORY structures.

Now, let’s examine the Optional Header as it appears in a real PE file.

Data Directories

The last member of the Optional Header is the Data Directories, and it’s worth taking a closer look.

What Are Data Directories?
In the IMAGE_OPTIONAL_HEADER structure, the Data Directories are represented as an array of IMAGE_DATA_DIRECTORY structures:

Each IMAGE_DATA_DIRECTORY has just two members:

In simple terms, a Data Directory points to a specific type of data stored somewhere in the PE file sections. The VirtualAddress is an RVA pointing to that data, and the Size tells you how big it is.

Data Directories are used by the Windows loader to locate important information. For example, the Import Directory contains a list of functions imported from other libraries, which the loader needs to resolve before executing the program.

Section Headers

After the Optional Header and before the sections comes the Section Headers. Each section is preceded by a Section Header, which describes its properties. The structure is defined as:

members:

  • Name – Section name (max 8 characters).
  • VirtualSize – Total size of the section when loaded in memory.
  • VirtualAddress – RVA of the section start relative to the image base.
  • SizeOfRawData – Size of the section on disk (rounded to FileAlignment).
  • PointerToRawData – File offset to the section’s data.
  • Characteristics – Flags describing the section (executable, writable, shared, etc.).

Sections

After the headers, the rest of the PE file is divided into sections. Sections are containers for the executable’s actual data: code, resources, and other necessary information.

Some common section names:

  • .text – Executable code
  • .data – Initialized data
  • .bss – Uninitialized data
  • .rdata – Read-only initialized data
  • .edata – Export tables
  • .idata – Import tables
  • .reloc – Relocation information
  • .rsrc – Resources (images, icons, embedded binaries)

PE Imports

PE imports are a core mechanism in Windows executable files that list the external DLLs (Dynamic Link Libraries) and specific functions a program needs to run, such as system API calls. They allow the operating system’s loader to map necessary code, such as kernel32.dll, into memory, enabling functionality like file handling or network access.

Key components of PE imports include:

  • Import Directory Table: An array of descriptors, one for each imported DLL, marking the start of the import data.
  • Import Lookup Table (ILT/INT): A table holding pointers to the names or ordinals (IDs) of the functions to be imported.
  • Import Address Table (IAT): A table updated at runtime by the loader, which replaces the function names with the actual memory addresses of those functions, enabling direct calls.

Import Directory Table

The Import Directory Table sits at the start of the .idata section. It is essentially a Data Directory that lists all the DLLs imported by the executable.

It’s made of an array of IMAGE_IMPORT_DESCRIPTOR structures—one per DLL. The array ends with a zeroed-out entry to mark the end.

  • OriginalFirstThunk: RVA pointing to the Import Lookup Table (ILT) for this DLL.
  • Name: RVA of an ASCII string containing the DLL name.
  • FirstThunk: RVA of the Import Address Table (IAT).
  • ForwarderChain: Usually 0 unless the DLL forwards functions to another DLL.
  • TimeDateStamp: Typically 0, not used for unbound imports.

Import Lookup Table (ILT) / Import Name Table (INT)

The ILT tells the loader which functions to import from the DLL. Its RVA is stored in OriginalFirstThunk.

  • PE32: 32-bit entries
  • PE32+: 64-bit entries

The ILT ends with a zeroed-out entry.

ILT entry format:

  • MSB (Bit 31/63): Ordinal/Name flag
    • 1 → import by ordinal
    • 0 → import by name
  • Other bits:
    • Ordinal mode: stores the 16-bit ordinal of the function
    • Name mode: stores the RVA of a Hint/Name Table entry

Hint/Name Table

The Hint/Name Table contains the names of functions to import:

  • Hint: A number used as a quick index into the DLL’s export table.
  • Name: Null-terminated string with the function name.

When the loader processes the ILT, it uses the Hint and Name to resolve the function’s actual address in the DLL.

Import Address Table (IAT)

The IAT is where the executable ultimately calls imported functions.
On disk, the IAT is identical to the ILT.
When the binary is loaded, the loader overwrites each entry with the real address of the imported function in memory.
